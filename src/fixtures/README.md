# Example persons

`persons.csv` is taken from the BRP mock the application is checked against,
[personen-mock](https://github.com/BRP-API/Haal-Centraal-BRP-bevragen/tree/master/test-data/personen-mock)
(`ghcr.io/brp-api/personen-mock`, `docker compose up -d personen-mock`).

Four out of five rows match the mock exactly, so the BRP check reports nothing
for them. The remaining fifth carries a mistake, together covering nearly every
finding the check can produce: values the BRP holds differently or not at all,
candidates it records as deceased, not Dutch or excluded from the right to vote,
residences without a `woonplaats`, and burgerservicenummers that are missing,
unknown or confirmed absent. Three rows exercise the fallback search on personal
details: a typo'd number and a missing one are resolved to the right person
anyway, and the confirmed-absent one belongs to a `Precise` sibling, ten of whom
share a surname and date of birth, so no combination of details can tell them
apart. Three findings are absent: `BsnNotUnique`, which the mock cannot serve
because it keys its records on the burgerservicenummer, `LastNameNotAllowed`,
which needs a candidate with a partner in the mock and a name that fits neither,
and `Unparsable`, because the one value the mock holds in an unusual shape (a
`voorletters` of 53 initials with a digit among them) is one `Initials` accepts,
so it comes out as a difference instead.

`brp_agrees_with_four_out_of_five_fixture_candidates` in `persons.rs` checks
this against the running mock. The rows with a mistake are spread over the first
fifty-five, so they end up on the fixture candidate list.

## Columns

`geslachtsnaam` holds the prefix as it is written on the candidate list ("de
Bruin"); `split_last_name_prefix` splits it off again. The address columns are
the person's correspondence address and are not checked against the BRP; the
`woonplaats` is.

## Regenerating from the mock

```sh
fields=$(jq -r '.[] | [
    .burgerservicenummer,
    .geslacht.code,
    .naam.voornamen,
    ((.naam.voorvoegsel // "") + " " + .naam.geslachtsnaam | ltrimstr(" ")),
    .geboorte.datum,
    .verblijfplaats.straat,
    .verblijfplaats.huisnummer,
    .verblijfplaats.postcode,
    .verblijfplaats.woonplaats
] | @csv' test-data.json)

echo "burgerservicenummer,geslacht,voornamen,geslachtsnaam,geboortedatum,straat,huisnummer,postcode,woonplaats" > output.csv
echo "$fields" >> output.csv
```

# BRP findings

`brp_findings.json` is what the BRP answered about the candidates above: the
findings per candidate for the one in five that carries a mistake, generated by
running the BRP client against the mock rather than written by hand. The CSB
fixture records them as a finished BRP check for one of its political groups,
so the examination has a group with findings on it without a BRP being
reachable.

Candidates the BRP agreed with are left out; the `candidate` of each entry is
there to read, the `person` is what the fixture keys on.

## Regenerating from the mock

`brp_findings_are_what_the_mock_answers` in `brp_findings.rs` rewrites the file
whenever the mock answers differently, which is also how it was written in the
first place:

```sh
docker compose up -d personen-mock
cargo test --features development -- --ignored brp
```
